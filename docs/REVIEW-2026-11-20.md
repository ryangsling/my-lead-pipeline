## Summary

**Verdict: no for a live US contractor demo today. Ready to demo after the fixes: yes**, once the booking, call-routing, consent, and urgent-callback paths below pass an end-to-end test on the actual US Vapi number.

The database does prevent two hub callers from taking the same slot in one workspace. I reran the test that makes 20 simultaneous attempts. It produced **one booking, one Google insert against the mock, and 19 conflicts**. PostgreSQL enforces non-overlap from start through the end of the buffer, even when the requests race. The remaining risks are outside that guarantee. [Constraint](/workspace/my-lead-pipeline/drizzle/0001_booking_lock_and_rls.sql:2) · [Concurrency test](/workspace/my-lead-pipeline/tests/int/booking.test.ts:49)

The **top three risks** for this market are:

1. The receptionist can offer an unverified slot or tell a caller that nothing was booked when Google already created the event.
2. An urgent caller can spend minutes on the line without reaching a person or triggering an owner alert. A missing end-of-call report can suppress the alert entirely.
3. A shared Vapi number can be reassigned from one contractor to another through the normal admin UI. The checked-in evidence also leaves inbound phone answering unverified.

I reviewed commit `f939ccb`. Typecheck, lint, all **49 unit tests**, and all **105 integration tests** passed during this review. No source changes were made.

## Findings by severity

### High

1. **Google can report a calendar error with HTTP 200 and the hub will offer the day as free.** `getBusy` substitutes `[]` when the requested calendar or its `busy` field is missing. It ignores the calendar-level `errors` array and caches the result for 60 seconds. A revoked or unavailable calendar can therefore yield convincing spoken availability. A thrown HTTP error takes the callback path, but a slow request has no application-level deadline here. Require the requested calendar, a valid busy array, and zero calendar errors before caching or offering slots. Bound the read by the voice-tool deadline and return the callback option on timeout. **Effort S.** [Calendar response handling](/workspace/my-lead-pipeline/src/lib/google/calendar.ts:76) · [Voice fallback](/workspace/my-lead-pipeline/src/lib/tools/run.ts:77)

2. **A hub booking and a Google event can permanently disagree.** The hub commits a `booked` row, creates the Google event, then saves its ID. If Google accepts the event but the response is lost, or the subsequent DB update fails, the catch deletes the row. The caller hears “nothing is booked yet” while the dispatcher sees an event. A process exit after the initial insert leaves the opposite state. Rescheduling moves Google *before* the new DB interval wins its exclusion check. An independent edit in Google can also race the fresh free/busy check. Use a durable pending reservation that holds the interval, a deterministic Google event ID, and reconciliation for ambiguous results. Reserve the target before moving an event and retain the previous interval until the move is resolved. Explicitly handle reactivation of cancelled appointments, which currently changes status without recreating the deleted event. **Effort L.** [Booking write order](/workspace/my-lead-pipeline/src/lib/booking/book.ts:65) · [Reschedule and cancellation](/workspace/my-lead-pipeline/src/lib/booking/status.ts:72)

3. **Assigning a number can silently divert another contractor’s calls.** The dropdown lists the account’s phone numbers without filtering existing assignments. Selecting one patches its remote assistant, then deletes local rows belonging to the selected workspace **or** that phone number. With two businesses sharing the global Vapi account, an admin setting up B can redirect A’s published number to B. Replacing a workspace’s number also removes the old local mapping without detaching its old remote number. Show only available numbers, resolve the E.164 value from Vapi, reject ownership conflicts, and make deliberate reassignment a separate, reconciled operation. **Effort M.** [Number listing and assignment](/workspace/my-lead-pipeline/src/app/api/workspaces/[id]/phone-numbers/route.ts:19) · [Cross-workspace deletion](/workspace/my-lead-pipeline/src/app/api/workspaces/[id]/phone-numbers/route.ts:55)

4. **A failed end-of-call job can permanently lose a lead or notification.** The webhook acknowledges after inserting the raw event. Processing runs in `after()`, and a duplicate delivery schedules work only if a *new* event row was inserted. Restart the function after the insert or fail ingestion once: Vapi’s retry gets 200 and performs no recovery. The dedupe key also omits workspace, despite authenticating the workspace before insertion. Store workspace on the inbox row, distinguish pending/processing/succeeded/retryable states, and let a worker reclaim incomplete rows. Keep transcript replacement and notification dedupe when retrying. **Effort M.** [Webhook receipt and dispatch](/workspace/my-lead-pipeline/src/app/api/vapi/webhook/route.ts:49) · [Event persistence](/workspace/my-lead-pipeline/src/lib/vapi/events.ts:6) · [Unique key](/workspace/my-lead-pipeline/src/lib/db/schema.ts:284)

5. **An urgent lead has no dependable 60-second delivery path.** `capture_lead` updates the conversation and promises a callback. Voice notifications wait for the end-of-call report. Delivery retries after 1, 3, and 9 seconds inside the same invocation, with no explicit fetch deadline or durable reclaim of a pending send. A five-minute call already misses a 60-second target measured from disclosure of the emergency. A provider accepting a message before the `sent` update fails can also cause duplicate delivery. Public bookings schedule notifications after the booking succeeds, so a transport failure does not roll back the appointment. Enqueue urgent events during the call, persist attempts and deadlines, and escalate to a backup channel or person on missed acknowledgement. **Effort M.** [Lead capture](/workspace/my-lead-pipeline/src/lib/tools/run.ts:130) · [Voice notification trigger](/workspace/my-lead-pipeline/src/lib/notifications/events.ts:51) · [Retry and log updates](/workspace/my-lead-pipeline/src/lib/notifications/send.ts:35)

6. **Tool retries can contradict a successful booking.** The route echoes `toolCallId` but neither requires it nor stores a receipt keyed by it. If the success response is lost, the identical retry usually finds the slot occupied and tells the caller it is unavailable. A subsequent request for an alternative can create a second appointment for the same job. The exclusion constraint prevents two *overlapping active rows* in the workspace, not two different slots in one call. Claim a unique `(workspace, call, toolCallId)`, persist the result/reference, and replay that response. Tie booking intent to the durable reservation in finding 2. **Effort M.** [Tool execution and logging](/workspace/my-lead-pipeline/src/app/api/vapi/tools/route.ts:62) · [Conflict response](/workspace/my-lead-pipeline/src/lib/tools/run.ts:119)

7. **Recording is enabled regardless of what the caller hears or agrees to.** The first-message validator checks for the words “AI” and a substring matching “record.” A greeting can mention “your service record” and pass. Sync unconditionally enables recording. For interstate US calls, a notice alone cannot establish the consent required in every applicable jurisdiction. Use a fixed disclosure, configure recording policy per workspace, and provide a tested consent/refusal or unrecorded handoff flow. Confirm with counsel when capture may start, and verify the actual Vapi behavior before using real callers. **Effort M.** [Notice validator](/workspace/my-lead-pipeline/src/lib/agent/store.ts:24) · [Vapi recording configuration](/workspace/my-lead-pipeline/src/lib/vapi/assistant-config.ts:24)

8. **The 90-day retention setting does not delete the data.** The hub retains names, phone numbers, email, appointment notes, transcripts, tool arguments/results, summaries, structured fields, recording links, and raw webhook bodies in Postgres. Google event descriptions can contain contact details and notes. Vapi holds call artifacts, and Telegram/email recipients receive notification copies. Expiry of a signed playback URL does not delete the recording. The repository also contains a real captured fixture with call-monitor and artifact URLs. Implement expiry for the raw and derived copies, provider-side deletion and a verifiable deletion log. Sanitize the fixture while retaining its shape. Establish separate retention terms for Google events, backups, and delivered messages. **Effort L.** [Raw webhook storage](/workspace/my-lead-pipeline/src/lib/vapi/events.ts:6) · [Google event contents](/workspace/my-lead-pipeline/src/lib/booking/event.ts:18) · [Captured fixture](/workspace/my-lead-pipeline/tests/fixtures/vapi/end-of-call-report.json:9) · [Unimplemented retention work](/workspace/my-lead-pipeline/docs/PLAN.md:446)

9. **The public booking endpoint can consume appointment capacity without verifying the lead.** The embed key is intentionally public. The route writes a contact before it validates the service/slot through the booking engine, and there is no rate limit or caller verification on this path. Repeated invalid requests can leave junk contacts. Separate valid requests can occupy a contractor’s estimate calendar. Add per-workspace and per-originating-client rate limits, validate the booking before committing lead data, and give contractors an optional verification or request-only mode. An origin allowlist alone would not establish caller identity. **Effort M.** [Public booking handler](/workspace/my-lead-pipeline/src/app/api/public/[pk]/book/route.ts:19) · [Public key resolution](/workspace/my-lead-pipeline/src/lib/booking/public.ts:5)

### Medium

10. **The voice tool validates that a time is currently open, but never proves that this caller was offered it.** The server accepts any nonempty `start`, permits an offsetless local time, and checks it against all valid starts for the day. Thus an invented but open 11:30 appointment can succeed even though the assistant offered only 9:00, 9:30, and 10:00. Conversely, the route discards the structured ISO-slot list and returns only spoken text to Vapi. Names and phones accept whitespace at schema validation, optional email lacks format validation, and tool strings/batch length have no useful caps. Require a short-lived offered-slot ID bound to workspace, call, and service, then revalidate availability at commit. Trim and bound arguments, require a usable callback number, validate calendar dates/email, and reject malformed tool-list entries. **Effort M.** [Tool schemas](/workspace/my-lead-pipeline/src/lib/tools/run.ts:14) · [Offered slots](/workspace/my-lead-pipeline/src/lib/tools/run.ts:77) · [Day-wide validation](/workspace/my-lead-pipeline/src/lib/booking/book.ts:46) · [Voice response](/workspace/my-lead-pipeline/src/app/api/vapi/tools/route.ts:67)

11. **Archiving a workspace leaves its synced voice assistant operational.** The public booking key checks `status = active`. Vapi authentication joins to the workspace and checks its secret with an equal-length, timing-safe comparison, but never checks workspace status. A retired contractor’s still-connected number can continue accepting tools and booking work. Disable new tool actions on archive, detach the number, and define a narrow policy for accepting final reports from calls already underway. **Effort S–M.** [Vapi authentication](/workspace/my-lead-pipeline/src/lib/vapi/auth.ts:17) · [Workspace archive](/workspace/my-lead-pipeline/src/lib/workspaces.ts:100)

12. **Vapi sync is repeatable only after a complete successful save.** It patches known IDs and recreates on 404, but holds newly created remote IDs in memory until *all* tools, the structured output, and the assistant succeed. A failure creating the last resource, a lost response, or two concurrent syncs can leave duplicates. Edits made before a later failure can also leave the live assistant using a mixture of versions. Serialize sync per assistant/account, checkpoint each remote ID, record a desired-config hash, and reconcile remote state before retrying uncertain creates. Recheck the US phone binding if the assistant ID changes. **Effort M.** [Remote create/update](/workspace/my-lead-pipeline/src/lib/vapi/sync.ts:26) · [Final checkpoint](/workspace/my-lead-pipeline/src/lib/vapi/sync.ts:93)

13. **Provider errors bypass the vault’s normal masking boundary.** The vault uses AES-256-GCM, a base64-decoded 32-byte environment key, a fresh 12-byte random IV, and an authentication tag. The normal settings view masks declared secrets. The exception is error handling: provider response text can be stored as `lastError`, `syncError`, or notification log `error`, then shown in the UI. If a provider echoes request data, that copy is plaintext. I found a path for disclosure, not evidence that a particular key was disclosed. Store bounded, redacted error codes/messages and test an upstream error containing a sentinel credential. **Effort S.** [Encryption](/workspace/my-lead-pipeline/src/lib/crypto.ts:4) · [Raw provider error](/workspace/my-lead-pipeline/src/lib/integrations/testers.ts:13) · [Client-facing error](/workspace/my-lead-pipeline/src/lib/integrations/service.ts:19) · [Notification log](/workspace/my-lead-pipeline/src/lib/notifications/send.ts:40)

14. **Overnight dispatch and repeated DST hours do not fit the schedule model.** Appointment instants use `timestamptz`; notice, horizon, weekday and slot generation use the business zone. But settings reject `close <= open`, so 8 p.m.–6 a.m. cannot be entered as one shift. Closing-time validation fits the service duration while allowing its buffer to extend beyond closing. On fall-back night, two distinct 1:30 a.m. instants can have the same spoken label. “Tomorrow morning” is translated to a date by the model using a zoned prompt; the server receives only that date, and silently changes a past date to today. Support overnight intervals, define whether travel buffers must fit the shift, and resolve relative dates server-side.
